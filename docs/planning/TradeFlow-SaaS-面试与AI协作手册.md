# TradeFlow SaaS：面试、正确性证据与 AI 协作手册

配套：[总计划](./TradeFlow-SaaS-项目总计划.md) · [56 天每日任务](./TradeFlow-SaaS-56天每日计划.md)。

技术栈：NestJS、TypeScript、PostgreSQL、Prisma、Redis、RabbitMQ、Jest、Docker；前端 Vue 3、Vite、Vue Router、Pinia、Element Plus、Axios、ECharts。前端关键测试使用 Vitest / Vue Test Utils，浏览器流程使用 Playwright。

这是个人求职项目的学习与表达手册。以下问题为按项目设计的模拟追问，不声称来自某家公司的实际面试。

## 1. “掌握”要达到什么程度

| 等级 | 能做什么 | 对项目的要求 |
|---|---|---|
| 1 知道 | 解释术语与用途 | 所有写进简历的名词至少达到 |
| 2 实现 | 找到代码，说清输入、输出、依赖 | 所有核心模块达到 |
| 3 验证 | 正常/反例都能跑，能解读数据库结果 | 权限、交易、消息、报表必须达到 |
| 4 取舍 | 对比替代方案，用实测或约束作判断 | 库存事务、幂等、Outbox/Inbox 至少三个亮点达到 |

AI 能帮你完成第二级的初稿，但不能自动让你掌握第三、四级。每天关掉 AI，用自己的话讲一遍关键流程。

## 3. 60 个面试追问

3. Node 单线程为什么仍然会出现并发超卖？多个进程又增加了什么风险？
4. 事件循环被 CPU 工作阻塞时用户会看到什么？如何定位？
5. 分页导出为什么适合 stream / 背压？一次读全量数据有什么问题？
6. NestJS Module、Provider、Controller 的职责如何分配？
7. Pipe、Guard、Interceptor、Exception Filter 分别放什么逻辑？
8. 请求级租户上下文如何传到应用服务、数据库和后台任务？
9. 事务中的服务调用如何保证使用同一个事务客户端？
10. 模块化单体什么时候应该拆成独立服务？你的项目为什么暂不拆？

**证据**：代码结构、DTO、错误映射、异步执行器、事务参数传递方式。

13. on_hand、reserved、available 分别表示什么？为什么支付后不立即出库？
14. 多 SKU 下单中一个不足，如何证明其他 SKU 没有残留预占？
15. 重复 SKU 行为什么要先合并？统一操作顺序如何减少死锁？
16. Read Committed、Repeatable Read、Serializable 有什么区别？Serializable 失败后如何重试？
17. 什么地方用乐观 version，什么地方用行锁或条件更新？
18. CHECK、唯一约束、外键、业务服务各守住哪些不变量？
19. 为什么 tenant_id 过滤之外还需要组合外键？
20. Prisma 能帮你什么？什么情况下需要参数化 SQL？
21. 金额用分与 BIGINT 后，JS 和 JSON 边界怎样处理？
22. 为什么订单价格必须快照？修改 SKU 价格后历史报表应怎样变化？
23. 库存流水与余额如何对账？为什么不同时间点查询会误报？
24. 订单列表复合索引怎么定列顺序？如何通过 EXPLAIN 验证？

**证据**：状态表、SQL、数据库约束、并发反例、查询计划和对账脚本。

### 请求幂等、支付与流程

32. 模拟退款成功但本地超时未知，如何避免再次退款？

## 4. 如何写一份可信的并发实验报告

```markdown
# C01：10 件库存 / 100 个独立订单请求
## 环境
- Git SHA、应用/数据库/MQ 版本：
- CPU / 内存、API 实例数、DB 连接池：
- 初始 SKU、仓库、租户、库存：
- 请求总数、目标并发、重试规则、随机 seed：

## 预期
- 正常依赖下最终 10 单成功，其余库存不足。
- 没有负库存；reserved 与有效预占一致。

## 实测
- 业务成功：
- 库存不足：
- 幂等处理中/冲突：
- 网络/超时/其他系统异常：
- 吞吐、p50/p95、样本量：
- 重复轮数、失败轮数：

## 最终业务状态
- 订单数量、有效 reservation、流水汇总：
- 核对 SQL 与结果文件：
- 消息投影追平情况：

## 结论与限制
- 当前结果支持什么：
- 哪些故障或规模没有覆盖：
- 失败反例和修复前后证据：
```

不要只截取终端里“success 10”。同时核对库存、预占、流水和数据库业务事实。系统异常存在时不能把全部剩余 90 个请求都叫库存不足。

不要承诺任意网络分区、磁盘损坏下零丢失。说明演练覆盖的进程退出、消息重投、短时依赖断连以及持久化假设。数据一致性的保证来自事务与约束设计，测试提供所覆盖场景下的验证证据。

## 5. 每周需要补的基础

| 周 | 每天约 30 分钟 | 独立练习 |
|---|---|---|

| 3 | MVCC、隔离、锁、死锁、幂等 | 解释并修复先查后写竞态 |
| 4 | 消息确认、重试、事件顺序、最终一致 | 手画发布/消费六个崩溃窗口 |
| 5 | HTTP、Cookie、CSRF、对象级授权；Router/Pinia | 带取消和错误处理的查询 composable |
| 6 | Jest fixtures、集成测试、性质测试、故障注入 | 不看 AI 写一个并发验证用例 |

| 8 | 编码/SQL/系统设计/表达 | 两次模拟面试与一个现场修复 |

另外选 12–20 道基础数据结构题，覆盖哈希、栈队列、堆、二分和复杂度。强算法笔试岗位需要另外安排刷题，不能靠业务项目替代。

## 6. 日常 AI 协作提示词

### 开工与拆解

```text
今天执行 TradeFlow SaaS 的 Day NN：[贴当天任务]。
先阅读 docs/planning、最近 devlog、相关实现和测试，判断实际进度。
给出最小修改方案、涉及文件、事务/权限/状态边界、验收命令。
只做今天授权的范围，优先完成未通过的关键不变量。
前端使用 Vue 3 + TypeScript + Vite + Router + Pinia + Element Plus。
不要引入第二套订单服务或不必要的微服务。
```

### 实现一个交易改动

```text
本次只实现：[下单预占 / 取消释放 / 收货 / 发货]。
先列出操作前提、状态迁移、读取/更新的表、唯一约束、锁顺序与事务范围。
说明重复调用、并发调用、事务回滚、提交后响应丢失时会发生什么。
确认方案后分小步实现，所有业务写入使用同一事务客户端。
不要在持有数据库事务时调用外部 HTTP 或 MQ。
不能只用 mock 验证数据库并发；新增与本次风险相关的真实集成测试。
```

### 反例审查

```text
请审查当前 diff，优先找真实的：
超卖、重复预占/释放/出库、金额不一致、状态回退、跨租户/客户访问、
先 ACK 后提交、Outbox/Inbox 不同事务、缓存串租户、旧请求覆盖新 Vue 页面。
每条发现写触发顺序、影响、代码位置与最小修复建议。
没有证据的疑点标为待验证，不编造问题。
```

### 并发测试设计

```text
为不变量 [填写] 设计测试。
使用真实 PostgreSQL、多连接；关键场景通过两个 API 进程。
先定义最终合法状态，再设计 barrier 或故障点控制竞争窗口。
输出业务成功、业务拒绝、系统失败的分类，核对数据库最终事实。
保留 seed、初始数据、环境配置和复现命令。
不要把 Promise.all 的存在本身当作已验证真正并发。
```

### Vue 页面实现

```text
根据现有 API 实现 [页面]，使用 Vue 3 Composition API、script setup、TypeScript、
Element Plus、Vue Router 与 Pinia；复用现有 Axios 请求层。
明确加载、空数据、失败、权限不足、冲突、提交中状态。
表格使用服务端分页；切换租户和筛选时取消或忽略旧请求。
前端权限仅控制展示，业务授权由后端独立检查。
不在 store 或组件里实现第二套价格、库存扣减和状态规则。
```

### 代码口述与面试

```text
根据今天真实代码，问我五个递进问题：用途、执行流程、一个竞态、替代方案、保证边界。
一次只问一个，等我先回答，不提前给标准答案。
最后指出我讲不清的代码，以及一个需要我独立完成的小改动。
```

### 提交拆分

```text
根据当前 diff 建议 2–3 个逻辑清晰的提交边界。
提交分别体现实际功能/修复、关键验证、确有新增的设计或实验说明。
不要空提交、伪造日期、为了数量拆碎一行代码，也不要写未经执行的测试结果。
```

## 7. 一个有价值的开发日提交例子

以 Day 17 为例：

```text
feat: persist tenant-scoped order idempotency results
test: cover duplicate submissions and lost responses
docs: explain idempotency conflicts and retention
```

PR 示例描述：

> 重复点击下单或响应丢失后的重试可能创建多张订单。现在请求幂等记录与订单、库存预占同事务提交，同 key 同内容返回原结果，不同内容返回冲突。
>
> 验证：真实 PostgreSQL 上的并发重复、参数冲突和提交后响应丢失场景；最终仅一张订单、一组预占和流水。保证范围受幂等键作用域与保留期约束。

建议每周一次自审整理，保留有意义的细粒度提交；一个 PR 不必包含几百行无关 AI 生成代码。正常日 2–4 个提交，复盘或休息日不硬凑。提交图不是能力证明，能追踪的决策与验证才是。

## 9. 三段演示讲稿

### 90 秒介绍

“我做的是面向中小贸易企业的多租户平台，采购入库、客户订货和后台订单共用同一套库存交易逻辑。后端使用 NestJS、PostgreSQL/Prisma、Redis、RabbitMQ，前端是 Vue 3。重点是交易正确性：下单通过数据库事务原子预占，重复请求通过持久化幂等结果恢复，异步事件用 Outbox/Inbox 处理重投。我用真实数据库和两个 API 实例验证了 [实际场景]，保留测试与对账报告。项目采用模拟支付，当前限制是 [实际限制]。”

### 5 分钟业务展示

1. 切换企业与角色，展示权限和数据隔离。
2. 建采购单、审批、收货，查看库存流水。
3. 客户订货、模拟支付、仓管发货。
4. 看报表与审计，展示数据来源和更新延迟。
5. 打开 README 的证据与限制。

### 5 分钟技术深挖

1. 展示 100 请求抢 10 件库存的环境与结果。
2. 展示重复请求返回同一订单，核对预占与流水。
3. 消费提交后断开，重启重投，展示 Inbox 防重复。
4. 对账输出无差异，解释覆盖范围与失败假设。
5. 展示一个真实失败反例、修复与复验。
