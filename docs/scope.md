# Day 1：业务范围与约束

日期：2026-10-23。依据 [总计划](planning/TradeFlow-SaaS-项目总计划.md) 与 [每日计划](planning/TradeFlow-SaaS-56天每日计划.md)。本文件定义未来业务验收，不表示业务已实现。

## 三条用户故事

1. **采购入库**：作为采购员，我建立 10 件键盘的采购单，提交给管理员批准；仓管一次性全量收货后，现存库存增加 10，并生成入库流水和审计。重复收货只生效一次，未批准不能收货，任一步失败整单回滚。
2. **客户订货与模拟支付**：作为租户所属客户，我从该企业订货页购买 2 件键盘；后台业务员也通过同一个下单应用服务代客下单。服务端读取价格、保存快照，原子预占库存；重复请求返回原结果，库存不足整单失败。有效模拟支付成功后转为已支付，继续保留预占。
3. **发货与取消边界**：作为仓管，我将已支付订单整单发货，现存与预占同时减少 2，并记录出库流水和审计；重复发货不重复扣减。未付款到期取消释放预占，晚到的支付进入模拟退款补偿，不能复活订单。另一租户及未获授权客户不能查看或操作这张订单。

## 固定业务边界

- 单币种 **CNY**，金额为整数分；后续数据库 BIGINT / TypeScript bigint，JSON 使用十进制字符串。客户端总价不作为权威。
- 每订单只属于一个仓库，数量为正整数；重复 SKU 先合并，按仓库/SKU 固定顺序操作。
- `available = on_hand - reserved`；`on_hand >= 0`、`reserved >= 0`、`reserved <= on_hand`。
- 下单增加预占；支付不扣库存；取消释放预占；发货同时减少现存和预占。
- 订单路径：`PENDING_PAYMENT → PAID → SHIPPED → COMPLETED`，或 `PENDING_PAYMENT → CANCELLED`。重复事件不能使状态倒退。
- 支付与取消竞争先锁订单，取得锁后读取实际数据库时钟判断截止时间，不能使用客户端时钟或事务开始时间替代。
- 业务状态、库存余额/流水、幂等结果、审计与 Outbox 同事务；事务内不调用外部 HTTP/MQ。消费者业务与 Inbox 同事务，提交后 ACK。
- 租户来自已验证身份和成员关系；同时核验角色与资源归属，客户账号再受 customer 归属限制。核心关系用租户组合外键约束。
- PostgreSQL 是业务真相；Redis 和 Vue 状态不承担库存正确性。全部使用合成数据和模拟支付，不涉及真实资金。

## 不做项

不做自定义权限平台、完整组织树、复杂 CRM、部分收货、采购退货、供应商结算、多币种、优惠券、税务、拆单、部分发货、已支付用户取消、完整售后、批次/序列号、成本核算及会计报表。多仓调拨、RLS、Kubernetes 等选做项不进入当前主线。
